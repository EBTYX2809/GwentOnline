# UI: что переиспользуем, а что придётся переделать в веб-версии

**Контекст:** нынешняя "графика" в WPF-клиенте — это не рисованные ассеты, а jpg-скриншоты/кропы
из оригинальной мини-игры Гвинт из Ведьмака 3 (`Gwent_Release/Images/*.jpg`: арт карт, обложки
колод по фракциям, фоны меню/стола), которые выводятся через WPF `ImageBrush`, привязанный к
абсолютным координатам `Canvas.Left`/`Canvas.Top` при фиксированном размере окна 1680×1050
(`Gwent_Release/Views/MainWindow.xaml`, `Menu.xaml`). Вопрос был — можно ли что-то из этого
переиспользовать в веб-версии, или всё нужно переделывать с нуля ради нормальной адаптивности.

## Что переиспользуется на 100% как есть

- **Все файлы изображений** — арт карт, обложки колод фракций, фоны стола/меню
  (`Images/*.jpg`). Jpg есть jpg, ничего WPF-специфичного в них нет. Они напрямую подключаются в
  любом веб-стеке (тег `<img>` / CSS `background-image`) без единой переделки.
- **Структура контента** за ними — `JsonNameKey` на карту, одна картинка на карту, локализованные
  название/описание на карту в `JsonLanguages/CardsInfo{EN,RU,UA}.json` — это чистая, переносимая
  модель данных вне зависимости от фронтенд-стека. См. `docs/ARCHITECTURE.md`, §4/§5.
- Один момент стоит держать в голове, но не срочный: этот арт взят из оригинальной коммерческой
  игры (CDPR). Для личного/хобийного проекта, как сейчас — нормально; стоит пересмотреть только
  если проект когда-нибудь станет более публичным/коммерческим.

## Что придётся переделывать

Не графику — **систему позиционирования**. Сейчас каждый элемент на столе размещён по жёстко
заданным пиксельным координатам на `Canvas` при фиксированном разрешении — адаптивности нет
вообще никакой (см. `docs/UI_VISUALS.md`, §1, §6). На вебе это нужно превратить в настоящую
адаптивную раскладку (сетки/флекс-контейнеры вместо ручных чисел `Left`/`Top` на каждый элемент).

Хорошая новость: борд Гвинта — удачный случай для этого. Это в основном **равномерные сетки
одинаковых карт, выстроенных рядами** (3 ряда на игрока + рука + погодный ряд), а не произвольная
иллюстрация — то есть один из более простых кейсов для нормальной адаптивной раскладки,
сравнительно говоря.

Два конкретных механизма, которые в WPF собраны руками, на вебе ожидаемо станут даже проще, а не
сложнее:

- **Drag & drop.** В WPF-версии вручную собран поддельный "призрак" карты при перетаскивании —
  клонируется визуал карты и вручную перепозиционируется под курсором каждый кадр
  (`CreateCardVisual` + `GameDesk_DragOver` в `MainWindow.xaml.cs`), потому что WPF не даёт этого
  из коробки. Нативный drag&drop в браузере тоже кривой, но в экосистеме любого крупного
  веб-фреймворка есть зрелые библиотеки под drag&drop, которые решают проблему призрака/
  позиционирования/подсветки цели прямо из коробки — руками это переизобретать не должно
  понадобиться.
- **Тултипы/hover-состояния** (имя/описание карты при наведении) на вебе заметно проще, чем в WPF
  (`ToolTip` + ручное переключение цвета рамки через `MouseEnter`/`MouseLeave`) — на вебе это
  нативный CSS `:hover` или базовый паттерн тултипа.

## Вариант, который стоит держать в уме: пиксель-перфект через масштабируемый контейнер

Если визуальное соответствие нынешней раскладке важно (то есть "хочу, чтобы выглядело и
ощущалось так же, только чтобы было адаптивно") — это не противоречит адаптивности. Контейнер с
фиксированным соотношением сторон, который масштабируется целиком под размер экрана (а не каждый
элемент репозиционируется по отдельности), может сохранить точный нынешний вид и при этом
работать на любом экране. Стоит рассмотреть, когда начнётся реальная работа над раскладкой, как
альтернативу полному редизайну визуального расположения борда с нуля.
