# Тестируемость и архитектура под будущий ИИ (веб-версия)

**Контекст:** в WPF-версии игровую логику было почти невозможно тестировать кодом — единственный
способ проверить сценарий был реально запустить два клиента и сыграть партию вручную. Причина,
конкретно: методы движка блокируются на колбэках в UI прямо посреди выполнения. Пример —
`BattleRow.AddCardToBattleRow` (`Gwent_Release/Models/PlayerNS/BattleRow.cs`) делает
`await GiveMedicCardToContext?.Invoke(...)` — сам движок ждёт попап от UI, чтобы доиграть
розыгрыш карты. Пока код движка может "заблокироваться и спросить у UI", он не может работать
headless (без интерфейса), а значит не может быть покрыт юнит-тестами и не может управляться
ботом.

Плюс ты хочешь в будущем добавить ИИ-оппонента, и сам подметил связь: бот — это по сути "код,
который правильно выбирает ходы", а это структурно та же задача, что и "код, который проигрывает
сценарий для теста". Одна архитектура должна закрывать обе потребности сразу.

## Рекомендуемый дизайн (не привязан к стеку — веб-стек ещё не выбран)

1. **Состояние партии = обычные данные.** Никакого синглтона (`GameContext.Instance`), никаких
   статических классов с изменяемым состоянием (`TurnManager`, мутации в `CardsStore` и т.д. как
   сейчас). Состояние — это сериализуемый снепшот: руки, колоды, отбои, ряды на столе, чей ход,
   счёт раунда и т.д.
2. **Ход = обычные данные.** Например `PlayCard(cardId, row)`, `Pass`, `ChooseTarget(cardId)`. Не
   вызов метода с побочными эффектами внутри.
3. **Чистая функция применяет ход к состоянию:** `(состояние, ход) → новое состояние` (+
   опционально список событий — для анимаций/лога/объявлений). Никакого `await` UI-ввода внутри
   этой функции, никогда.
4. **Многошаговые взаимодействия карт — это два последовательных хода, а не один блокирующий
   метод.** Сейчас Medic-воскрешение, Decoy и кражи карт лидерами (Эмгыр/Фольтест) работают через
   то, что метод движка приостанавливается и ждёт ответ от UI. Вместо этого: первый ход (например
   "сыграть Medic") должен переводить состояние в явное подсостояние "жду выбора: выбери карту из
   вот этих N в отбое"; второй ход ("выбрать карту X") его разрешает. Это делает даже такие
   многошаговые взаимодействия тривиально тестируемыми: применяем ход 1 → проверяем состояние
   "жду выбора" → применяем ход 2 → проверяем итоговое состояние стола.
5. **Общая функция "список легальных ходов из этого состояния".** Нужна трём разным потребителям
   с одинаковым интерфейсом:
   - Юнит-тесты — проверить ожидаемый набор легальных ходов в данном сценарии.
   - UI — понять, что можно перетащить/куда можно бросить карту, что подсветить.
   - Будущий ИИ — это и есть его пространство выбора для перебора/оценки.

   Сделать это один раз и правильно — вероятно, самая ценная часть всей переработки движка.

## Почему это стоит зафиксировать уже сейчас

- Это архитектурное решение **дня первого**, а не то, что можно докрутить потом — нынешний
  кодбейз как раз демонстрирует, что бывает, если движок и UI не разделены с самого начала (см.
  `docs/ARCHITECTURE.md`, §3, "known issues" — там описано, в какой конкретно форме это
  вылилось в C#).
- Это прямой ответ на твою озвученную боль ("тестировать этот проект было чуть-ли не возможно,
  приходилось каждый раз запускать новые партии").
- Это напрямую готовит почву под ИИ-оппонента, который ты отложил на потом — отдельной работы по
  "интеграции ИИ" не должно понадобиться, если функции "легальные ходы" и "применить ход"
  спроектированы достаточно универсально с самого начала.

## Открытые вопросы на момент реальной реализации

- Точная форма структур данных для состояния/хода (будет зависеть от выбранного стека/языка).
- Останется ли "подсчёт очков с приоритетами" (погода → Bond → Buff → Horn, см.
  `docs/GWENT_RULES.md`, §6) простым производным вычислением над новой структурой состояния, или
  ему нужна отдельная чистая функция — скорее всего второе, и это, вероятно, самая простая часть
  для переноса — почти напрямую из существующей логики приоритетов в `EffectModifiersStore.cs`.
- Куда впишется серверная валидация ходов, когда добавится мультиплеер (сейчас WPF-клиент
  полностью доверяет любой строке хода, присланной соперником — см. `docs/NETWORKING.md`, §3;
  функция "легальные ходы" выше — это же естественное место для валидации входящих ходов на
  сервере в мультиплеере, а не только для управления UI/ИИ).
